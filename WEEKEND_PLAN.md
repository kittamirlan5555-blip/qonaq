# WEEKEND_PLAN — план автономных сессий (главнее TASKS.md)

Этот файл — единственный источник задач для автономных сессий. Каждая сессия стартует «с нуля»,
без памяти о прошлых. Владелец не отвечает: не задавай вопросов, решения пиши в `DECISIONS.md`.

## Протокол каждой сессии (обязательно)

1. Ветка `claude/bold-fermat-de51i5`. `git pull`. Если последний коммит в ветке моложе 20 минут —
   другая сессия ещё работает: **ничего не делай и заверши работу**.
2. Прочитай `CLAUDE.md`, `PROGRESS.md`, этот файл, `DECISIONS.md`. В таблице «Статус» ниже найди первую
   задачу не в статусе ✅ и продолжай с неё (внутри задачи — по чек-листу в `PROGRESS.md`).
3. Окружение: `.venv`, `pip install -e ".[dev]"`, плюс `scikit-learn`. **torch и ultralytics не ставить**
   (в облаке качаются часами). Детектор — YOLOX через onnxruntime, как раньше.
   Видео: `python scripts/fetch_videos.py`. Датасеты: `python scripts/fetch_datasets.py` (см. W1).
4. Коммить и пушь **после каждого законченного куска, не реже раза в 30–40 минут**. Сессия может
   оборваться по лимиту в любой момент; незакоммиченное пропадает. Перед каждым коммитом — `pytest` и `ruff check`.
5. После каждой задачи: обнови таблицу «Статус» здесь и `PROGRESS.md` (что сделано, цифры, что не вышло).
6. Не коммить видео, датасеты, `runs/`. Маленькие веса (голова классификатора, ≤ 5 МБ) коммитить можно в `models/`.
   Сохраняемые кадры и видео с людьми — только с блюром.
7. Никаких выдуманных цифр. Каждая цифра точности — с описанием, на чём и как измерена.
8. Когда все задачи ✅ — напиши первой строкой `PROGRESS.md` «ВСЕ ЗАДАЧИ WEEKEND_PLAN ВЫПОЛНЕНЫ» и заверши.
   Следующие сессии, увидев эту строку, сразу завершаются.

Обязательно:
- **Единая схема.** Роли: `staff` ← waiter, staff, Staff, Worker, Waiter; `guest` ← customer, Customer;
  класс `person` из первого архива и прочие — игнор. Столы: `clean`, `dirty`, `occupied`.

  Внутри одного зала дополнительно — разбиение по дате/исходнику, только как «верхняя граница».
- Гостей для зала C (Ramada) добери детектором: люди, не пересекающиеся (IoU < 0.3) с разметкой Waiter.
- Кропы людей: bbox с небольшим полем, минимум ~24×48 px, слишком мелкие — в отдельную корзину и отдельную цифру.

## W2. Классификатор «персонал / гость»

Архитектурное решение (запиши в DECISIONS): **замороженный предобученный энкодер в ONNX + лёгкая голова**
(логистическая регрессия/маленький MLP из scikit-learn, экспорт в numpy/ONNX, чтобы в рантайме sklearn не требовался).
Причины: не нужен torch; голова обучается за секунды на CPU — это же делает возможной калибровку под зал
на мини-ПК при установке (W6). Признаки = эмбеддинг энкодера + HSV-гистограммы торса и ног (уже есть в `roles/uniform.py`).

- Энкодер: возьми ONNX-модель с GitHub (onnx/models, PINTO0309 model zoo и т.п. — raw.githubusercontent / releases
  доступны; HuggingFace — нет). Предпочтительно person-ReID (OSNet) или лёгкий ImageNet-энкодер (MobileNetV3/EfficientNet-lite).
  Сравни 2 варианта на leave-one-venue-out, выбери по качеству и скорости (цель ≤ 5 мс на кроп на CPU, батчами).
  Лицензию проверь (нужна разрешительная). Скрипт загрузки — `scripts/fetch_models.py`.
- Метрики в EVAL.md по каждому отложенному залу: balanced accuracy, precision/recall по `staff`, PR-кривая точками,
  матрица ошибок; отдельно для мелких кропов. Сравни с базой «только HSV-гистограммы».
- Интерфейс `RoleClassifier` в `qonaq/roles/`; в `tracker.py` — слияние по треку (голосование по окну):
  внешний вид + поведение. Поведенческие правила: **сидит в зоне стола дольше порога → гость** (официантам
  сидеть с гостями запрещено); стоит + короткий заход 4–90 с → кандидат в персонал; обход нескольких столов — усиливающий.
  Итог: роль + уверенность; `unknown`, если сигналы расходятся.
- Прогони на 5 видео, покажи в EVAL.md, изменились ли цифры сверки и ложный/пропущенный `staff_visit`.

## W4. Синтетика полного цикла

`python -m qonaq synth`: фон — пустой кадр (`topdown_cafe_empty` и пустой кадр CCTV-ролика), по сценарию из YAML
движутся вырезанные из датасетов фигуры (гости — из `guest`, официант — из `staff` одного зала, чтобы форма была
одинаковой), на стол после ухода накладывается «посуда». Разметка событий генерируется из сценария.
Сценарии: обычный визит; официант не подошёл 3+ минуты; гость вышел на минуту и вернулся; гости ждут друга
30 минут после подхода официанта (алерта быть не должно); ушли, стол не убрали 5+ минут.
Прогон через весь пайплайн и `eval`; результаты в EVAL.md с пометкой «синтетика».

## W6. `qonaq calibrate` — калибровка под зал

Сценарий установки: сутки записи → автокалибровка → 15 минут ручной проверки → новая голова.
- `calibrate collect`: из прогона сохраняет кропы людей с признаками и поведенческой авторазметкой
  (уверенный гость: сидел в зоне ≥ N минут; уверенный персонал: стоя обошёл ≥ K столов / короткие визиты).
- `calibrate review`: локальная веб-страница — сетка неуверенных кропов (лицо размыто, одежда видна), клики «персонал / гость / пропустить».
- `calibrate train`: дообучает голову на (общие датасеты + кропы зала с большим весом), проверяет на отложенной
  части размеченного вручную, пишет «было X% → стало Y%», сохраняет версию в `models/site/<site>/vN/`.
- Новая версия включается только командой `calibrate promote`; `calibrate rollback` возвращает прошлую.
  **Никакого полностью автоматического самообучения** — модель не должна учиться на собственных ошибках без проверки.
- Проверка идеи без нового зала: возьми отложенный зал из W2, дай калибровке 50/100/300 его кропов и построй
  кривую «сколько размеченных примеров → какая точность». Это главный аргумент для разговора с клиентом; в EVAL.md.

## W7. Монитор здоровья

`qonaq health` + фоновая проверка в live: камера не отвечает / кадр тёмный или замёрзший; стол переключается
чаще N раз в час; неправдоподобные события (ожидание > 40 мин, сессии < 60 с подряд, ноль визитов персонала за смену);
доля `unknown`-ролей. Ежедневная сводка владельцу системы в Telegram (отдельный chat id): статус, число посадок,
5 размытых кадров с подписями состояний для выборочной проверки. Кнопка «неверно» под алертом → запись в таблицу
обратной связи (пригодится калибровке). Тесты на синтетике.

## W8. Уверенные алерты

Алерт администратору отправляется, только если состояние подтверждено достаточной уверенностью ролей
(порог в конфиге); неуверенные случаи идут в отчёт, но не в Telegram. Тесты. Цель — лучше пропустить алерт, чем отправить ложный.
