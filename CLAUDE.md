# Qonaq Vision — инструкции для Claude Code

Ты работаешь над проектом **Qonaq Vision** (қонақ = «гость»): видеоаналитика зала ресторана поверх
уже установленных камер видеонаблюдения. Система видит каждый стол как зону и в реальном времени
знает: стол свободен / гости сели и ждут официанта / их обслуживают / ушли и стол не убран.
Из этих событий считаются метрики (время подхода официанта, простой столов, оборачиваемость)
и деньги, которые заведение теряет.

Владелец проекта — Тамирлан, applied AI engineer (Python, LLM-пайплайны, Label Studio, Telegram-боты,
DevOps). Рынок — Казахстан. Первый реальный тест — на камерах клиники (зона ожидания + регистратура),
поэтому движок должен быть **общим**: «зоны + типы зон + профиль логики», а ресторан — это один профиль.

## Режим работы этой сессии

- Владелец спит. **Не задавай вопросов и не жди ответа.** Принимай разумное решение, записывай его
  в `DECISIONS.md` (что решил, почему, какие альтернативы) и иди дальше.
- Работай строго по `TASKS.md`, сверху вниз. Майлстоуны упорядочены так, что даже если сессия
  оборвётся на середине, уже сделанное полезно само по себе.
- После каждого майлстоуна: тесты зелёные → `git commit` → обновить `PROGRESS.md`
  (что сделано, как запустить, что не получилось, следующий шаг).
- Если что-то блокирует (не скачивается модель, нет GPU, нет видео) — запиши в `PROGRESS.md`
  раздел «Блокеры», сделай обходной путь или переходи к следующей задаче, которая не зависит от блокера.
- Не трать время на красоту раньше функциональности. Сначала работающий пайплайн на файле,
  потом всё остальное.

## Окружение

- Машина владельца — вероятно Windows, возможно с NVIDIA GPU. Проверь сам (`nvidia-smi`, `python --version`).
  Код должен работать на **Windows и Linux**: `pathlib`, никаких bash-only скриптов как единственного
  способа запуска; точки входа — Python CLI (`python -m qonaq ...`). Можно добавить `.ps1`/`.sh` обёртки.
- Python 3.11 или 3.12, виртуальное окружение `.venv` в корне проекта.
- PyTorch: если есть NVIDIA — поставь CUDA-сборку с официального индекса PyTorch под версию драйвера;
  если нет — CPU. Устройство выбирается автоматически, переопределяется в конфиге.
- Сессия может идти в облаке Claude Code (Linux, **без GPU**, интернет только через allowlist:
  PyPI, GitHub и raw.githubusercontent.com работают, YouTube — нет). На CPU используй `n`-модели и 2–3 fps.
- Тестовые видео: первым делом запусти `python scripts/fetch_videos.py` — он скачает 5 публичных записей
  в `data/videos/` (описание каждой — в скрипте; две главные — реальные CCTV ресторана и веранды, по ~1–1,5 мин).
  Записи короткие: для проверки длинных сценариев (уход через 90 с и т.п.) склей/зацикли или используй синтетику.
  Если скачать не удалось — не останавливайся: код и юнит-тесты на синтетике, в `PROGRESS.md` отметь это.
  Владелец позже добавит длинные записи и реальные камеры клиники.
- `data/`, `runs/`, `.venv/`, веса моделей, `.env` — в `.gitignore`. Видео в git не коммитить никогда.

## Стек (по умолчанию; отклонения — через DECISIONS.md)

- Детекция людей / столов / стульев: Ultralytics YOLO (последняя доступная версия, `n`/`s` размер;
  COCO-классы `person`=0, `chair`=56, `dining table`=60). Опционально pose-модель для «сидит/стоит».
- **Детектор — за интерфейсом `Detector`.** Ultralytics под AGPL-3.0; для коммерческого продукта
  его придётся заменить или купить лицензию. Поэтому никакого кода, завязанного на объекты ultralytics,
  вне адаптера. Запиши это в DECISIONS.md.
- Трекинг и зоны: `supervision` (MIT) — ByteTrack, PolygonZone, аннотаторы.
- Видео: OpenCV (`cv2.VideoCapture` для файла / вебкамеры / RTSP).
- Хранилище событий: SQLite (stdlib `sqlite3`), без ORM.
- Конфиги: YAML + pydantic-модели с валидацией.
- Веб-панель: FastAPI + один статический HTML/JS без сборщиков (SSE или WebSocket для live-статусов).
- Тесты: pytest. Линт: ruff.
- Алерты: Telegram Bot API через обычный HTTP (`httpx`), включается только если есть токен в `.env`.

## Архитектура (держись её)

```
qonaq/
  sources/      # VideoSource: file | webcam | rtsp; отдаёт (frame, ts_seconds); семплинг fps
  detect/       # Detector interface + ultralytics adapter; Detection(dataclass)
  track/        # обёртка над ByteTrack
  zones/        # модели зон, загрузка/сохранение, авто-предложение столов, редактор
  roles/        # staff vs guest: эвристики + калибровка по цвету формы
  logic/        # машины состояний по профилям (restaurant, clinic) — ЧИСТЫЕ функции от наблюдений
  events/       # SQLite-лог событий, схема, запись/чтение
  metrics/      # расчёт метрик и ROI из событий (не из видео!)
  render/       # аннотированное видео «как в рилсе» + блюр лиц
  api/          # FastAPI панель
  alerts/       # telegram
  pos/          # POSAdapter interface + mock + заглушки iiko/r_keeper/Poster
  cli.py        # точки входа
tests/
configs/        # профили и примеры зон
docs/
```

Ключевой принцип: **логика состояний не знает про видео.** На вход — поток наблюдений
`(ts, zone_id, guests_present, staff_present, ...)`, на выход — события. Это даёт тестировать
логику синтетическими таймлайнами без единого кадра.

Время: для файлов — время видео (`CAP_PROP_POS_MSEC`), для потоков — wall clock. Все пороги в секундах
времени сцены, а не кадрах.

## Качество

- Каждая машина состояний покрыта тестами на синтетических таймлайнах, включая шум:
  мигающая детекция, человек прошёл мимо стола, официант постоял 2 секунды, гость вышел покурить.
- Каждый CLI-сценарий из `TASKS.md` запускается на реальном видео из `data/videos/` (если есть),
  результат и наблюдения — в `docs/EVAL.md`.
- Не выдумывай метрики точности. Если меряешь — опиши как. Если не мерил — так и пиши.
