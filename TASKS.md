# TASKS — порядок работы

Иди сверху вниз. Каждый майлстоун: код → тесты → прогон (если есть видео) → commit → PROGRESS.md.
«Готово» = выполнены все пункты «Критерии». Если пункт невозможен (нет видео/GPU) — отметь почему.

---

## M0. Каркас и окружение
- [ ] `git init`, `.gitignore` (уже есть — проверь), `pyproject.toml`, пакет `qonaq/`, `tests/`.
- [ ] `.venv`, зависимости; PyTorch под CUDA если есть `nvidia-smi`, иначе CPU.
- [ ] `python -m qonaq doctor`: версии Python/torch/CUDA, устройство, найденные видео в `data/videos/`
      (длительность, fps, разрешение), доступность весов модели.
- [ ] `PROGRESS.md`, `DECISIONS.md` созданы.
**Критерии:** `python -m qonaq doctor` отрабатывает; `pytest` и `ruff check` зелёные.

## M1. Источник → детекция → трекинг → аннотированное видео
- [ ] `VideoSource` (file / `webcam:N` / `rtsp://...`), семплинг до `process_fps` (по умолч. 5),
      метка времени сцены. Для RTSP — реконнект с backoff.
- [ ] `Detector` интерфейс + ultralytics-адаптер (person/chair/dining table), порог уверенности в конфиге.
- [ ] ByteTrack через supervision; трек хранит историю позиций (нижняя центральная точка bbox).
- [ ] `python -m qonaq run-file data/videos/x.mp4 --out runs/x/` → видео с bbox и id треков.
- [ ] Блюр верхней части bbox людей в любом сохраняемом видео по умолчанию (`--no-blur` чтобы выключить).
**Критерии:** на каждом видео из `data/videos/` получается аннотированный mp4; fps обработки
записан в EVAL.md по каждому видео.

## M2. Зоны
- [ ] Pydantic-модели зон (`table`, `entrance`, `waiting_area`, `service_point`, `ignore`), YAML I/O.
- [ ] `zones suggest <video>`: авто-предложение столов из детекций `dining table` по N кадрам
      (кластеризация, расширение на стулья, нумерация T01…слева-направо/сверху-вниз) → YAML + превью-PNG.
- [ ] `zones edit <video|image>`: OpenCV-редактор (клики, Enter, Backspace, s — сохранить, тип зоны).
      Ночью GUI не проверить — сделай так, чтобы логика редактора была тестируема отдельно от окна.
- [ ] `zones preview`: PNG кадра с зонами.
- [ ] Присвоение трека зоне по нижней центральной точке bbox; зона `ignore` перекрывает остальные.
**Критерии:** для каждого видео есть `configs/zones/<video_stem>.yaml` из автопредложения и превью-PNG;
в EVAL.md — насколько адекватно авто-предложение (сколько столов нашёл / сколько видно глазами).

## M3. Логика стола + события (самое важное — максимум тестов)
- [ ] Наблюдение `ZoneObservation(ts, zone_id, guest_tracks, staff_tracks, unknown_tracks)`.
- [ ] Машина состояний `restaurant` ровно как в SPEC §5, пороги из конфига, гистерезис, dropout tolerance.
- [ ] SQLite: `events`, `sessions`; запись событий и закрытие сессий.
- [ ] Тесты на синтетических таймлайнах (минимум): обычный визит целиком; гость вышел покурить на 60 с;
      мигание детекции; прохожий через зону; официант 2 с (не визит) и 6 с (визит); ушли до обслуживания;
      сели за грязный стол; два визита подряд без уборки; несколько столов параллельно.
- [ ] Подключить к пайплайну: `run-file` пишет события в `runs/<name>/events.sqlite`.
**Критерии:** ≥ 15 тестов логики зелёные; на реальном видео события пишутся; в EVAL.md —
ручная сверка на одном видео (что произошло по факту vs что записала система).

## M4. Гость vs персонал
- [ ] Эвристики из SPEC §4.1 (dwell + малое движение = гость; короткий заход = визит; ≥3 столов за 5 мин = персонал).
- [ ] Голосование роли по окну трека, роль не скачет.
- [ ] `roles calibrate <video>`: сохраняет кадры с id треков в `runs/calib/`, принимает список id сотрудников
      (аргументом CLI, без GUI) → HSV-гистограммы торса → `configs/staff_profile.yaml`.
- [ ] Классификатор по профилю формы, комбинируется с эвристикой (уверенности).
- [ ] Опционально pose «сидит/стоит» — только если остаётся время, за флагом.
**Критерии:** тесты эвристик на синтетике; на реальных видео — в EVAL.md примеры удачных и неудачных случаев.

## M5. Демо-рендер «как в рилсе»
- [ ] Полупрозрачные полигоны: зелёный FREE, жёлтый SEATED_WAITING (с таймером, краснеет после порога),
      синий SERVED, серый/оранжевый NEEDS_CLEANING. Подпись `T03 · FREE` / `T02 · 2 гостя · 02:14`.
- [ ] Боковая панель: таблица всех столов (статус, занято, ждёт, свободно), загрузка зала %, время.
- [ ] Флаг ускорения (`--speed 4`) для коротких демо из длинных записей.
- [ ] `python -m qonaq demo data/videos/x.mp4` → `runs/x/demo.mp4` (с блюром).
**Критерии:** демо-ролик на каждом видео; выбери лучший и опиши в PROGRESS.md как «показывать его».

## M6. Метрики, отчёт, ROI
- [ ] Метрики SPEC §7 из SQLite (не из видео).
- [ ] ROI в ₸ по формуле SPEC §7, только пиковое время; входные параметры в YAML объекта.
- [ ] `python -m qonaq report runs/x/` → `report.html` (понятный не-технарю, по-русски, с оговорками
      о точности), `report.md`, `telegram.txt` (≤ 10 строк).
**Критерии:** отчёт генерируется для каждого прогона; числа в отчёте сходятся с событиями (тест).

## M7. Live: вебкамера/RTSP, панель, алерты
- [ ] `python -m qonaq live --site configs/sites/demo_webcam.yaml` — тот же пайплайн на потоке.
- [ ] FastAPI: `/` — кадр (MJPEG, с блюром) + статусы зон + таймеры + лента алертов; `/api/state`, `/api/events`.
- [ ] Алерты (SPEC §5) → Telegram, если в `.env` есть `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`;
      очередь и ретраи при обрыве сети; дедупликация (один алерт на событие).
- [ ] Пример `configs/sites/demo_webcam.yaml` (вебкамера ноутбука, одна зона-«стол» на пол-кадра)
      — владелец завтра проверит на работе.
**Критерии:** live запускается на видеофайле в режиме «как поток» (эмуляция реального времени) и
панель обновляется; без токена Telegram всё работает, алерты пишутся в лог.
