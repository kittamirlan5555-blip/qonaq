# KZ_REALITIES — железо, софт и условия Казахстана

## Камеры и регистраторы

Что реально висит в кафе/клиниках КЗ (и СНГ в целом):
- **Hikvision / HiWatch** (бюджетная линейка Hikvision) — самое частое.
- **Dahua** (и её бюджетные линейки), **Uniview (UNV)**, **Tiandy**, **Trassir** (у Trassir свой софт
  с аналитикой — потенциальный конкурент), **EZVIZ** / Imou (Wi-Fi камеры в маленьких кафе).
- Дешёвые no-name регистраторы на платформе **XMeye / iCSee**.

Типичные свойства картинки, под которые надо проектировать:
- 2–4 Мп, объектив 2.8 мм, камера в **углу под потолком** → сильная перспектива, дальние столы мелкие
  и перекрыты ближними людьми. Иногда fisheye на потолке.
- Камеры ставили «для охраны»: смотрят на кассу и вход, а не на столы. Часть столов будет не видна —
  это нормально, система должна честно показывать «покрытие» (сколько столов в кадре).
- Вечером/ночью — ИК-режим, ч/б картинка; тёплый тусклый свет в ресторанах; мерцание ламп.
- OSD поверх кадра: дата/время, название камеры — не путать с объектами, можно маскировать.
- **Используем substream** (второй поток, 640×360…704×576): его хватает для людей и столов,
  он не грузит регистратор и сеть. Mainstream — только если люди слишком мелкие.
- Регистраторы ограничивают число одновременных RTSP-подключений и иногда перезагружаются —
  нужен реконнект с экспоненциальной задержкой.

Шаблоны RTSP (в README и в `configs/examples/`; проверить на месте, у прошивок бывают отличия):
- Hikvision / HiWatch: `rtsp://USER:PASS@IP:554/Streaming/Channels/102` (канал 1, substream;
  `101` — mainstream, `202` — канал 2 substream).
- Dahua / Imou: `rtsp://USER:PASS@IP:554/cam/realmonitor?channel=1&subtype=1` (`subtype=0` — main).
- XMeye / iCSee: `rtsp://IP:554/user=USER&password=PASS&channel=1&stream=1.sdp?real_stream`
- Uniview: `rtsp://USER:PASS@IP:554/unicast/c1/s1/live` (s0 — main).
- Пароли в `.env`, не в YAML и не в git.

Для тестов без регистратора: вебкамера ноутбука (`source: webcam:0`) или телефон как IP-камера
(Android-приложения типа «IP Webcam» отдают HTTP/RTSP поток) — это почти реальный RTSP.

## POS-системы (Phase 2, интеграция через адаптер)

- **iiko** — очень распространена в ресторанах КЗ/СНГ; есть облачное API (iikoCloud) — первая
  интеграция по приоритету: получить открытые заказы и привязку к столам.
- **r_keeper** — крупные рестораны и сети, «тяжёлая артиллерия»; интеграция обычно через
  интеграторов/XML-интерфейс — вторая очередь.
- **Poster** — популярен у кофеен и небольших кафе в КЗ, REST API.
- MVP: `POSAdapter` интерфейс + `MockPOS` (генерирует открытия/закрытия чеков по сценарию)
  + заглушки с TODO и ссылками на документацию. Ничего не выдумывать про конкретные эндпоинты —
  оставить TODO, где детали надо сверить с официальной документацией.

## Сеть и размещение

- Интернет в заведениях бывает нестабильным → всё работает **локально**, алерты в Telegram
  с очередью отправки при обрыве.
- Железо на объекте: б/у мини-ПК или ПК с GPU уровня GTX 1660 / RTX 3050 на 4–8 камер; без GPU —
  1–2 камеры на CPU при 2 fps.
- Автозапуск как служба (Windows: планировщик задач / NSSM; Linux: systemd) — описать в docs.

## Язык и формат

- Интерфейс и отчёты на **русском**, строки вынесены для будущего казахского.
- Деньги — в **₸**, формат `45 000 ₸`. Время — Asia/Almaty (UTC+5, единая зона РК с 2024 г.).
- Канал уведомлений — **Telegram** (а не email/Slack). WhatsApp — потом.
- Отзывы гостей — **2ГИС** (в материалах упоминать его, а не Google Maps).

## Право (кратко, не юрконсультация)

- Видео с людьми = персональные данные по закону РК «О персональных данных и их защите»;
  биометрия (лица) — особая категория. Поэтому: без распознавания лиц, без хранения сырого видео,
  обработка на месте, блюр в демо, табличка «ведётся видеонаблюдение» у заведения обычно уже есть.
- В клинике — особенно аккуратно: пациенты. Только агрегаты, никаких сохранённых кадров с людьми
  без блюра.
