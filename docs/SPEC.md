# SPEC — Qonaq Vision

## 1. Что продаём одной фразой

«Подключаемся к камерам, которые у вас уже висят, и показываем в цифрах, сколько гости ждут официанта,
сколько столы стоят грязными и сколько денег вы на этом теряете. Без новых датчиков, без облака,
без распознавания лиц».

## 2. Пользователи

| Кто | Что ему нужно | Где смотрит |
|---|---|---|
| Владелец (часто несколько точек) | Цифры за смену/неделю, потери в ₸, сравнение точек | Отчёт в Telegram, веб-отчёт |
| Управляющий / админ зала | Какой стол сейчас требует внимания | Live-панель на планшете/мониторе, алерты |
| Официант | (не пользователь MVP) | — |

## 3. Зоны

Зона = полигон в координатах кадра конкретной камеры + тип + id + человекочитаемое имя.

Типы (общий движок, разные профили):
- `table` — стол с местами вокруг (ресторан). Полигон охватывает стол **и стулья**: сидящий гость
  определяется по нижней центральной точке bbox (ноги/таз) внутри полигона.
- `entrance` — вход/зона ожидания посадки (очередь).
- `waiting_area` — зона ожидания с сиденьями (клиника).
- `service_point` — стойка/регистратура/касса (клиника, бар).
- `ignore` — зоны, где люди не считаются (проход персонала, кухня в кадре, телевизор с людьми).

Источники зон:
1. **Автопредложение**: прогнать детектор `dining table` (+`chair`) по N кадрам, кластеризовать
   устойчивые детекции, расширить bbox стола на ~40% (захват стульев), выдать черновые полигоны.
   Это наша фишка для КЗ — установка за 10 минут, а не «пришлите интегратора».
2. **Редактор**: OpenCV-окно на кадре — клик по вершинам, Enter — закрыть полигон, ввод имени.
   Сохранение в `configs/zones/<camera_id>.yaml`. Также можно править YAML руками.
3. Предпросмотр: картинка кадра с наложенными зонами (`zones preview`).

## 4. Роли людей: гость vs персонал

Это главный технический риск. Многоуровневый подход, каждый уровень — отдельный модуль с флагом:

1. **Эвристика по поведению (по умолчанию)**: трек, который находится в зоне стола дольше
   `seat_min_s` (15 с) и почти не двигается (смещение центра < порога), — гость. Трек, который
   входит в зону занятого стола на 3–90 с и уходит, — «визит персонала». Трек, который за последние
   5 минут побывал у ≥ 3 разных столов, — персонал (сильный признак).
2. **Сидит/стоит** (опционально, pose): колени примерно на уровне таза или соотношение сторон bbox —
   сидящий. Стоящий у сидящих — кандидат в персонал.
3. **Калибровка формы**: владелец/установщик выбирает 3–10 кропов сотрудников (CLI показывает кадры
   с id треков), сохраняется HSV-гистограмма торса; классификатор по близости гистограмм.
   Автоматический режим: кластеризация торсов «многостольных» треков.
4. Задел на будущее: маленький классификатор на размеченных кропах (Label Studio экспорт).

Каждое решение о роли — с уверенностью; логика использует роль с гистерезисом по треку
(роль трека не скачет от кадра к кадру — голосование по окну).

## 5. Машина состояний стола (профиль `restaurant`)

```
FREE
  └─(гости в зоне ≥ seat_min_s)──────────────► SEATED_WAITING   [таймер ожидания]
SEATED_WAITING
  ├─(визит персонала ≥ visit_min_s)──────────► SERVED           [фикс. response_time]
  └─(гости ушли ≥ leave_min_s)───────────────► FREE (событие: walkout_before_service)
SERVED
  ├─(визит персонала)───────────────────────► SERVED (событие staff_visit, счётчик)
  └─(зона пуста ≥ leave_min_s)───────────────► NEEDS_CLEANING   [таймер простоя]
NEEDS_CLEANING
  ├─(визит персонала ≥ clean_min_s)──────────► FREE             [фикс. cleanup_time]
  └─(новые гости сели)──────────────────────► SEATED_WAITING (событие: seated_at_dirty_table)
```

Пороги по умолчанию (в конфиге профиля): `seat_min_s=15`, `visit_min_s=4`, `leave_min_s=90`
(гость вышел покурить/в туалет не должен освобождать стол), `clean_min_s=10`.
Все переходы — с гистерезисом; кратковременная потеря детекции (< `dropout_tolerance_s`=5) не меняет
состояние.

Алерты (настраиваемые): `no_waiter_s=180` (3 мин без подхода), `dirty_table_s=300`,
`long_service_without_visit_s=900` (гостей давно никто не проверял).
Phase 2 с POS: `occupied_without_check_s=600` — стол занят 10 минут, а чек в POS не открыт.

## 6. Профиль `clinic` (для теста на реальных камерах)

- `waiting_area`: число ожидающих, время ожидания каждого трека с момента входа в зону до
  перехода к `service_point` или ухода.
- `service_point`: очередь у стойки, время обслуживания, пустует ли стойка (нет сотрудника за ней
  при наличии очереди → алерт).
- Метрики: среднее/медиана/p90 ожидания, пиковые часы, «ушли не дождавшись».

## 7. События и метрики

Таблица `events(id, camera_id, zone_id, ts, type, payload_json)`; типы: `state_change`, `seated`,
`staff_visit`, `served`, `left`, `cleaned`, `alert`, `walkout_before_service`, …
Таблица `sessions` — сессия стола (от посадки до освобождения) с вычисленными длительностями.

Метрики (считаются только из событий):
- время до первого подхода (среднее, медиана, p90, доля > 3 мин);
- время простоя грязного стола; время «стол свободен» в пиковые часы;
- оборачиваемость (посадок на стол за смену), средняя длительность визита;
- визиты персонала на сессию; «столы-сироты» (давно без визита);
- загрузка зала по часам (heatmap час × стол);
- очередь у входа (если есть `entrance`).

**ROI / потери в ₸** (то, что отвечает директору «зачем мне это»):
вход — средний чек на стол (₸), смена, порог «пик» (загрузка ≥ 80% или очередь у входа > 0).
`потерянные_посадки = Σ(лишний простой грязного стола в пиковое время) / средняя_длительность_визита`
`потери_₸ = потерянные_посадки × средний_чек`. Считать **только пиковое время** (в пустом зале
грязный стол ничего не стоит) — консервативная, честная оценка. Отдельно — `walkout_before_service`.

## 8. Выходы MVP

1. **Демо-видео как в рилсе**: зелёные/красные полигоны, подписи `T03 FREE` / `T02 · 2 гостя · 02:14`,
   боковая панель со статусами и таймерами всех столов, счётчик загрузки. Опция `--blur-faces`
   (размытие верхней части bbox человека) — **по умолчанию включена** для любых сохранённых видео.
2. **Отчёт смены** (HTML + Markdown + короткое сообщение для Telegram): метрики из п.7, топ проблемных
   столов, оценка потерь в ₸, оговорки о точности.
3. **Live-панель** (FastAPI): схема зон поверх кадра камеры, статусы, таймеры, лента алертов.
4. **Алерты в Telegram** (если задан токен).

## 9. Приватность (обязательные свойства, не опции)

- Никакого распознавания лиц и идентификации личности. Треки — анонимные id, живут в пределах сессии.
- Обработка локально на месте (ПК/мини-ПК в заведении); в облако уходят только агрегаты и алерты.
- Сырое видео не сохраняется. Сохраняемые клипы/демо — с блюром.
- Это и юридическая необходимость (закон РК о персональных данных), и аргумент продаж.

## 10. Нефункциональные требования

- 2–5 обрабатываемых кадров/с на камеру достаточно; цель — 4 камеры на одном ПК с игровой видеокартой
  среднего уровня, 1 камера на CPU.
- Работа с потоком 640×360…1920×1080, H.264/H.265, ночной ИК-режим (ч/б) без падений.
- Переподключение RTSP при обрыве (регистраторы в КЗ часто перезагружаются / сеть нестабильна).
- Один YAML описывает объект: камеры, RTSP-адреса, профиль, зоны, пороги, средний чек.
