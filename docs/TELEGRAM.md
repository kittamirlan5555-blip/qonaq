# Telegram: кому что приходит и как подключить

Qonaq пишет в Telegram трём разным людям. Это три разных чата (можно личных, можно групп) у одного бота.

| Переменная в `.env` | Кто получает | Что приходит | Когда |
|---|---|---|---|
| `TELEGRAM_CHAT_ID` | администратор зала / менеджер смены | алерты по столам, под каждым кнопка «Неверно» | сразу, как случилось |
| `TELEGRAM_VENUE_CHAT_ID` | владелец заведения | итоги дня | раз в день, `alerts.shift_summary_at` (по умолчанию 23:30) |
| `TELEGRAM_OWNER_CHAT_ID` | владелец системы (тот, кто ставил) | техническая сводка с 5 кадрами (лица размыты), проблемы с камерами | раз в день, `health.daily_at` (23:40) + при проблеме |

Время в сообщениях — местное время заведения (`business.timezone`, по умолчанию `Asia/Almaty`, это UTC+5,
как и Астана с марта 2024). Номер стола берётся из зоны: `T05` пишется как «Стол 5»; если зоне дать имя
(`name: "Стол у окна"`) — пишется имя.

## Примеры всех сообщений

Получены командой `python -m qonaq telegram examples` — тем же кодом, что работает в системе (цифры синтетические).

### Алерты администратору

```
⚠ 11:54 · Стол 5: гости ждут официанта уже 3 мин (сели в 11:51)
⚠ 11:54 · Стол 2 не убран уже 5 мин (гости ушли в 11:49)
⚠ 11:54 · Стол 7: к гостям не подходили 16 мин
⚠ 11:54 · Стол 3 занят 10 мин, а счёт в кассе не открыт      ← только если подключена касса (POS)
```

Под каждым — кнопка **«Неверно»**. Нажатие записывается (таблица `feedback` журнала), бот отвечает
«Записано: неверно. Спасибо!». Эти отметки видны в технической сводке и нужны для калибровки.

В Telegram уходят только **уверенные** алерты (гости подтверждены как гости, уверенность ролей ≥ 0,6 —
`alerts.min_role_confidence`). Неуверенные видны в панели и считаются в сводке, но администратора не дёргают:
лучше пропустить алерт, чем приучить людей не верить боту.

Название заведения второй строкой — только если `alerts.show_site_name: true` (когда у одного администратора
несколько точек).

### Если пропал интернет

Алерты копятся в очереди и отправляются, когда связь вернётся (повторы с паузой 2 с → 4 с → … → 2 мин):

```
⚠ 11:54 · Стол 5: гости ждут официанта уже 3 мин (сели в 11:51)
Доставлено с опозданием: не было интернета.
```

Пометка ставится, если сообщение ушло позже чем через 2 минуты. Алерты старше 30 минут не отправляются вовсе
(«гости ждут» через полчаса уже бесполезно), но остаются в журнале и в отчёте. Один и тот же алерт дважды не
приходит (дедупликация по камере, столу, типу и посадке).

### Итоги дня — владельцу заведения

```
Qonaq · итоги дня · Кафе «Пример» · 14 ноября
Посадок за столы: 14
Официант подходил обычно за 1 мин 40 с; у худших 10% столов — дольше 3 мин 10 с
Ждали официанта дольше 3 мин: 3 стола из 14 (21%)
Ушли, не дождавшись официанта: 1
Столы убирали в среднем за 2 мин 09 с
Оценка упущенной выручки: около 15 000 ₸ (только часы пик и ушедшие)
Чаще всего проблемы: Стол 2, Стол 5, Стол 1
Это оценка по видео без проверки человеком.
```

«Обычно» — это медиана, «у худших 10%» — 90-й перцентиль; слова выбраны для владельца, формулы — в отчёте пилота.
Сводка считается по событиям с местной полуночи. Копия пишется в `runs/live_<объект>/shift_<дата>.txt`.

### Техническая сводка — владельцу системы

```
Qonaq · сводка за день · Кафе «Пример»
Статус системы: есть предупреждения
Посадок: 14, первых подходов официанта: 13, ушли: 14 (не дождавшись: 1)
Алертов: 2, из них неуверенных (не отправлены администратору): 1
Отметок «неверно» под алертами: 1
• cam2: кадр тёмный 75 с (свет выключен или камера закрыта)
• cam1: обрывов связи 1, без картинки всего 2 мин
Нагрузка: CPU 86% (100% = одно ядро), память 412 МБ; кадр/с по камерам: cam1 2.0, cam2 1.9
Ниже — кадры (лица размыты) для выборочной проверки: совпадают ли подписи с тем, что видно?
```

Следом — альбом из 5 кадров с подписями состояний столов (лица размыты). Смотреть 1 минуту в день: если подписи
расходятся с картинкой — пора калибровать или править зоны.

### Проблемы с камерами — владельцу системы, сразу

```
🛠 Кафе «Пример» · cam2: камера не отвечает 45 с
🛠 Кафе «Пример» · cam2: камера снова работает (не было 130 с)
```

Плюс прочие проверки монитора здоровья (тёмный/застывший кадр, «мигающий» стол, ожидание 40+ минут и т.п.) —
не чаще раза в час на одну проблему.

## Подключение: BotFather → токен → chat id → `.env`

1. В Telegram откройте **@BotFather** → `/newbot` → имя (например, «Qonaq Кафе Арман») → username, оканчивающийся
   на `bot`. BotFather пришлёт **токен** вида `123456789:AA...`. Это пароль бота — никому не пересылать.
2. Каждый получатель пишет боту `/start` (или бота добавляют в группу и пишут в ней любое сообщение).
3. На мини-ПК:
   ```
   # .env в корне проекта
   TELEGRAM_BOT_TOKEN=123456789:AA...
   ```
   ```
   python -m qonaq telegram chat-id
   ```
   Команда покажет chat id всех, кто писал боту (у групп id отрицательный, вида `-100...`).
4. Допишите в `.env`:
   ```
   TELEGRAM_CHAT_ID=...          # администратор
   TELEGRAM_VENUE_CHAT_ID=...    # владелец заведения
   TELEGRAM_OWNER_CHAT_ID=...    # вы
   ```
5. Проверка: `python -m qonaq telegram test --wait-press 120` — в каждый чат придёт «✅ Qonaq · …: проверка связи»,
   администратору — «🧪 Пример алерта» с кнопкой «Неверно», владельцу заведения (или администратору, если его
   чата нет) — «🧪 Пример итогов дня». Нажмите «Неверно» — команда покажет запись в таблице `feedback`
   (`runs/telegram_test/events.sqlite`). Без `--wait-press` нажатие не ждётся; `--only-ping` — только проверка связи.
6. Перезапустите службу (`python -m qonaq service restart` или вручную), чтобы она перечитала `.env`.

Если какой-то переменной нет — соответствующие сообщения просто не отправляются (пишутся в лог и файлы).

## Проверка без бота и без интернета

```
python -m qonaq telegram test --fake
```

Поднимает локальный фейковый Telegram Bot API (тот же формат `sendMessage`, `sendPhoto`, `sendMediaGroup`,
`answerCallbackQuery`, `getUpdates`) и прогоняет весь поток: алерт с кнопкой → нажатие «Неверно» → запись в
`feedback`; обрыв сети → очередь → доставка с пометкой; дедупликация; итоги дня; техническая сводка с кадрами.
Печатает, что «получил» каждый чат. То же проверяет тест `tests/test_sprint2.py::test_telegram_full_flow_on_fake_api`.

Ручная проверка с живой системой:

```
python -m qonaq telegram fake-server --port 8081          # окно 1
# окно 2: в .env или в окружении
TELEGRAM_API_BASE=http://127.0.0.1:8081 TELEGRAM_BOT_TOKEN=test TELEGRAM_CHAT_ID=100 python -m qonaq live --site ...
# что отправлено: http://127.0.0.1:8081/__fake/messages
```

`TELEGRAM_API_BASE` пригодится и в бою, если до api.telegram.org приходится ходить через свой прокси.

## Что проверено, а что нет

Проверено (облако, 14.11.2026): весь поток на фейковом API, тексты, очередь, дедупликация, кнопка.
**Проверено с настоящим Telegram (Windows 11, 14.11.2026):** проверка связи в три чата, пример алерта с кнопкой,
пример итогов дня, нажатие «Неверно» → строка в `feedback`. Найдено и исправлено: long polling `getUpdates`
обрывался по таймауту HTTP-клиента (10 с < 20 с ожидания), и нажатие подхватывалось с задержкой до 2 минут.
