# DECISIONS — решения, принятые без владельца

Формат: что решил → почему → какие были альтернативы. Новые решения — в конец.

## D-001. Python 3.12, окружение `.venv`, установка через `pip install -e .`
- **Что:** проект — обычный пакет с `pyproject.toml`; базовая установка `pip install -e ".[dev]"`,
  Ultralytics — опциональная группа `pip install -e ".[yolo]"`.
- **Почему:** одинаково работает на Windows и Linux, точка входа `python -m qonaq ...`.
- **Альтернативы:** poetry/uv-lock (лишняя сложность для MVP), requirements.txt (хуже с опциональными группами).

## D-002. Детектор только за интерфейсом `Detector`; Ultralytics — AGPL-3.0
- **Что:** весь код работает с `qonaq.detect.base.Detection` / `Detector`. `ultralytics` импортируется
  в единственном файле `qonaq/detect/ultra.py`. Ни один объект ultralytics не выходит за адаптер.
- **Почему:** Ultralytics YOLO распространяется под AGPL-3.0. Для коммерческого продукта придётся либо
  купить Enterprise-лицензию Ultralytics, либо заменить детектор. Интерфейс делает замену делом одного файла.
- **Альтернативы:** RT-DETR/D-FINE (Apache-2.0), YOLOX (Apache-2.0, см. D-003), собственная модель.

## D-003. Второй детектор «из коробки»: YOLOX через onnxruntime; `backend: auto`
- **Что:** добавлен адаптер `qonaq/detect/onnx_yolox.py` (YOLOX, Apache-2.0, готовые ONNX-веса из релиза
  на GitHub, инференс через `onnxruntime`). В конфиге `detector.backend: auto` означает:
  «ultralytics, если он установлен (стек по умолчанию из CLAUDE.md), иначе YOLOX-ONNX».
  `onnxruntime` — в базовых зависимостях, поэтому `pip install -e .` даёт рабочую систему без PyTorch.
- **Почему:** (1) в облачной сессии CPU-сборка PyTorch недоступна: `download.pytorch.org` закрыт сетевой
  политикой, а сборка с PyPI тянет ~3 ГБ CUDA-библиотек со скоростью < 1 МБ/с; (2) YOLOX под Apache-2.0 —
  это как раз кандидат на замену AGPL-детектора в коммерческой версии; (3) на рабочем ноутбуке утром
  установка без PyTorch занимает минуту.
- **Цена:** веса YOLOX старее (2021), на мелких людях слабее YOLO11. Компенсация — режим `onnx_tiles: 2`
  (полный кадр + две перекрывающиеся половины) и модель `yolox_m`. Сравнение — в `docs/EVAL.md`.
- **Альтернативы:** ждать установку torch (час+ и риск), экспортировать YOLO11 в ONNX (нужен torch и остаётся AGPL).

## D-004. `supervision` закреплён `<0.27`
- **Что:** в зависимостях `supervision>=0.22,<0.27`.
- **Почему:** в свежих версиях (проверено на 0.31.5) `sv.ByteTrack` удалён из пакета (трекеры вынесены
  в отдельный проект `trackers`). 0.26.x содержит ByteTrack и всё нужное.
- **Альтернативы:** пакет `trackers` (тянет лишние зависимости), свой трекер (незачем).

## D-005. В выходное видео попадают только обработанные кадры
- **Что:** аннотированное/демо-видео пишется с частотой `process_fps` (а не с частотой исходника).
- **Почему:** блюр привязан к детекциям конкретного кадра. Если дублировать рамки на пропущенные кадры,
  у идущего человека лицо «выезжает» из размытой области — это нарушение приватности. Заодно быстрее.
- **Альтернативы:** интерполяция рамок между кадрами (сложнее, всё равно риск утечки лица).

## D-006. Блюр: пикселизация верхней части bbox, включая неуверенные детекции
- **Что:** размывается верх bbox каждого человека (38% высоты для стоящих, 50% для «квадратных» bbox сидящих),
  причём для блюра берутся и детекции ниже порога трекинга (`detector.blur_conf`, по умолчанию 0.12).
  Блюр включён по умолчанию для любого сохраняемого кадра/видео; `privacy.save_raw_video` жёстко `false`.
- **Почему:** пропущенный детектором человек = неразмытое лицо; снижая порог только для блюра, уменьшаем
  этот риск без влияния на логику. **Ограничение:** человек, которого детектор не увидел совсем, останется
  неразмытым — перед публикацией ролик надо просмотреть глазами.
- **Альтернативы:** отдельный детектор лиц (ещё одна модель; на CCTV лица мелкие и находит он их хуже, чем людей).

## D-007. Видео пишется в H.264 через ffmpeg из пакета `imageio-ffmpeg`
- **Что:** кадры идут по pipe в ffmpeg (`libx264`, `yuv420p`, `+faststart`). Если ffmpeg не найден — OpenCV `mp4v`.
- **Почему:** `mp4v` из OpenCV не проигрывается в браузере и Telegram; демо-ролик должен открываться везде.
  `imageio-ffmpeg` ставит бинарник ffmpeg через pip и на Windows, и на Linux.

## D-008. Занятость стола — по скользящему окну присутствия, а не по id треков (SPEC §9a п.1)
- **Что:** `PresenceFilter`: окно `dropout_tolerance_s` (5 с), «включено» при доле положительных наблюдений
  ≥ 70%, «выключено» при ≤ 20%. Моменты событий выставляются задним числом (посадка = первое появление,
  уход = последнее наблюдение), поэтому гистерезис не искажает длительности.
- **Почему:** ByteTrack на косых камерах меняет id; таймеры стола не должны от этого сбрасываться.

## D-009. Как отличается визит персонала от «подсевшего гостя» без калибровки формы (SPEC §9a п.3)
- **Что:** у занятого стола каждый «не гость» открывает эпизод визита. Подтверждённый персонал (форма /
  ≥3 столов) засчитывается сразу при ≥ `visit_min_s`. Неизвестный засчитывается **после ухода**, если пробыл
  4–90 с, с `confidence: low`; если роли за это время признали его гостем — эпизод отменяется.
  Время реакции считается до **начала** визита.
- **Почему:** иначе опоздавший друг, подсевший к столу, считался бы «подходом официанта».
- **Следствие:** без калибровки формы статус SERVED появляется с задержкой на длительность визита;
  отчёт помечает долю событий с низкой уверенностью.

## D-010. Стол, занятый с первых секунд наблюдения, считается уже обслуженным
- **Что:** если гости сидят с самого старта потока (≤ `preexisting_grace_s`), сессия помечается
  `preexisting` и сразу переходит в SERVED; время подхода официанта для неё не считается.
- **Почему:** мы не знаем, сколько они уже сидят. Иначе каждый перезапуск системы давал бы ложные
  алерты «3 минуты без официанта» по всем столам. На коротких тестовых роликах это значит, что
  большинство столов сразу синие (SERVED) — это честно.

## D-011. Уборка, случившаяся до подтверждения ухода
- **Что:** уход гостей подтверждается через `leave_min_s` (90 с). Визиты персонала в этом окне
  откладываются: если гости вернулись — это обычные визиты; если уход подтвердился и был визит
  ≥ `clean_min_s` — стол сразу FREE, событие `cleaned` с реальным временем уборки.
- **Почему:** хороший официант убирает стол через 20 секунд после ухода; без этого правила такой стол
  висел бы «грязным» до следующего случайного визита.

## D-012. Пока фильтр гостей не «прогрет», занятость стола считается по фильтру «гости + неизвестные»
- **Что:** в сессии стола появился флаг `guest_confirmed` — фильтр присутствия гостей хотя бы раз включался
  за эту сессию. До этого момента «гости на месте / ушли» определяется по фильтру `_any` (гости + неизвестные).
  Плюс страховка: отсутствие в сессии не может начаться раньше самой посадки. `preexisting_grace_s: 0`
  теперь выключает правило «сидели до старта» совсем (раньше человек, видимый с первого кадра, всё равно
  считался «уже обслуженным», вопреки комментарию в демо-конфигах).
- **Почему:** баг ложных «ушли не дождавшись». Роль `guest` появляется через `seat_min_s` + окно голосования,
  и в момент посадки «по роли» фильтр гостей ещё выключен, а его отметка «пусто с…» указывает на старт потока
  (или на уход предыдущих гостей) — таймер ухода срабатывал мгновенно, с отрицательным временем ожидания,
  и так несколько раз подряд. Баг был возможен и с боевыми порогами (стол пустовал дольше 90 с — обычное дело).
- **Альтернативы:** только ограничить «пусто с…» моментом посадки — не спасает, если роль на кадр стала
  `guest` и вернулась в `unknown` (человек сидит, а стол «ушёл»); всегда считать занятость по `_any` —
  тогда официант, убирающий стол сразу после ухода гостей, продлевал бы «занятость».

## D-013. Кэш детекций на диске (инструмент разработки)
- **Что:** `qonaq/detect/cache.py` — обёртка над любым `Detector`, хранит рамки по хэшу содержимого кадра
  в `*.jsonl`. Включается `--det-cache DIR`, `detector.cache_dir` или переменной `QONAQ_DET_CACHE`.
  По умолчанию выключен. Изображения в кэш не попадают — только координаты, класс, уверенность.
- **Почему:** в облаке 2 ядра без GPU, режим качества даёт 0,6 кадр/с — один прогон 88-секундного ролика
  занимает 10 минут. Отладка логики/зон/ролей требует десятков прогонов одного и того же видео, а детекции
  при этом не меняются. На синтетических роликах (D2) неподвижные кадры повторяются — кэш даёт ускорение и там.
- **Альтернативы:** сохранять треки целиком (привязывает к версии трекера), кэш по номеру кадра (ломается
  при смене fps/обрезке).

## D-014. В «долю ожиданий дольше порога» входят и столы, к которым так и не подошли
- **Что:** в `share_over_threshold` учитываются незакрытые ожидания (ждут до сих пор) и уходы без обслуживания,
  если ожидание превысило порог; поле `unserved_over_threshold` — сколько таких.
- **Почему:** на перегенерированном прогоне веранды отчёт писал «ждали дольше порога: 0% столов» при трёх
  горящих алертах «нет официанта» — худшие случаи выпадали из статистики (ошибка выжившего).
- **Альтернативы:** оценка Каплана—Мейера для цензурированных ожиданий — избыточно для MVP.

## D-015. Датасеты качаются прямой ссылкой релиза, `gh api` — запасной путь
- **Что:** `scripts/fetch_datasets.py` берёт архивы по `https://github.com/<repo>/releases/download/data-v1/<имя>`
  (stdlib `urllib`), распаковывает в `data/datasets/<slug>/`, ставит маркер `.done`. Если прямая ссылка не сработала
  (например, репозиторий закрыт), пробует `gh api -H "Accept: application/octet-stream" …/releases/assets/<id>`.
  `Table.Cleanliness` качается только с `--all` (в обучении не используется).
- **Почему:** прямая ссылка работает в облаке и на Windows без установленного `gh`; ~1 ГБ скачался за пару минут.

## D-016. Индекс объектов вместо папок с кропами; критерий «мелкого» кропа — по площади
- **Что:** `python -m qonaq data index` пишет `data/index/{roles,tables}.csv`: путь к кадру, bbox, единая метка,
  зал/камера, группа для разбиения. Кропы на диск не сохраняются — признаки считаются с исходного кадра и
  кэшируются как числа (`data/features/*.npz`). «Мелкий» кроп: площадь < 24×48 px или короткая сторона < 16 px
  (в пикселях кадра датасета).
- **Почему:** не плодим тысячи неразмытых вырезок людей на диске (правило блюра); индекс — единый источник для
  всех разбиений. Порог по площади, а не «ширина ≥ 24 и высота ≥ 48»: сидящие люди сверху почти квадратные,
  и по сторонам в «мелкие» ушло бы почти всё.
- **Дубли:** один кадр на исходник (`<исходник>_jpg.rf.<hash>`), предпочтение valid/test (Roboflow аугментирует
  только train). Кадры `cam*` из `Dirty.Table` — это те же 632 исходника с той же разметкой, что в `Clean.Table`,
  поэтому из `Dirty.Table` берутся только `photo_*` (и 2 прочих кадра).
- **Группы:** роли — зал (A/B/C/D) для leave-one-venue-out; внутри зала — блок времени по номеру кадра
  (A: 500 кадров, B: 100, C: 50) или дата записи (D) — для «верхней границы». Столы — камера `camN`;
  все `photo_*` — одна группа `photo` (это несколько разных камер без имени; кластеризация миниатюр
  смешивала камеры, поэтому держим их вместе — так строже).

## D-017. Классификатор роли: замороженный ONNX-энкодер + лёгкая голова (по WEEKEND_PLAN W2)
- **Что:** признаки = эмбеддинг энкодера (L2-норм.) + HSV-гистограммы торса и ног (корень, 256 чисел);
  голова — логистическая регрессия scikit-learn (сравнение с MLP — в EVAL.md); рантайм — numpy, веса в `.npz`
  (`qonaq/roles/head.py`), sklearn в рантайме не нужен. Энкодеры — из `opencv/opencv_zoo` (Apache-2.0):
  MobileNetV2 ImageNet, обрезанный до глобального пулинга (1280), и Youtu ReID (768). Оба переделаны на вход
  любого размера (пакет `onnx`, только при подготовке, extras `[train]`).
- **Почему:** не нужен torch; голова учится секунды на CPU — это и есть калибровка под зал при установке (W6).
- **Альтернативы:** OSNet (на GitHub нет готового ONNX, только .pt — нужен torch для экспорта;
  HuggingFace закрыт), дообучение энкодера (нужен torch и GPU).

## D-018. Гости зала C (Ramada) добраны детектором
- **Что:** `yolox_m`, уверенность ≥ 0.5, человек с IoU < 0.3 со всеми рамками Waiter → `guest`, `origin=mined`.
- **Шум:** глазами просмотрено 64 случайных добранных «гостя» — 4–6 из них похожи на официантов (жилет/стоят),
  т.е. ~6–9% шума меток. Кроме того, в зале C всего несколько разных гостей (одни и те же люди на 470 кадрах),
  поэтому цифра по C говорит скорее «отличаем этих нескольких людей от официантов в жилетах».

## D-019. Энкодер для ролей — MobileNetV2 (не ReID); общая голова по умолчанию выключена
- **Что:** сравнение на leave-one-venue-out (EVAL.md §6): MobileNetV2 и Youtu ReID дают одинаково близкую к
  случайной точность на новом зале (среднее A,B,C 0,54–0,57 balanced accuracy), «верхняя граница» (данные того же
  зала в обучении) — 0,90–0,94 у обоих. MobileNetV2 в 4 раза быстрее (4,3 против 16,9 мс/кроп на 2 CPU,
  вход 160×96) и весит 9 МБ против 107. Выбран MobileNetV2, вход 160×96.
- **Общая голова `models/roles_head.npz`** (4 зала) сохранена, но `roles.classifier` по умолчанию `None`:
  на двух CCTV-роликах она **добавила** ложные визиты персонала (EVAL.md §6). Включать только голову,
  откалиброванную под зал (W6, `models/site/<site>/active.npz`).
- **Почему так:** форма персонала у каждого заведения своя; «как выглядит официант вообще» из 4 залов не выучивается.
  Это главный вывод W2 и аргумент за калибровку при установке.

## D-020. Стоящий у стола — «гость» только через 60 с; подмена id трекером сбрасывает историю
- **Что:** (1) `roles.standing_guest_min_s = 60`: правило «долго в зоне стола → гость» для стоящего срабатывает
  не через `seat_min_s` (15 с), а через 60 с. (2) Если рамка трека резко меняет пропорции (≥ 1,7×) **и** одежда
  (гистограмма торса) другая (похожесть < 0,5), это другой человек на том же id ByteTrack — новый стабильный id,
  история «сидел N минут» не наследуется. Гистограмма торса теперь считается всегда (дёшево).
- **Почему:** на синтетике (W4) официант, 20 с убирающий пустой стол, становился «гостем» → ложная «посадка за
  неубранный стол»; официант, подошедший к гостям, получал от ByteTrack id гостя и с ним историю — визит не
  засчитывался, срабатывал ложный алерт «нет официанта». Оба случая возможны и в реальности.
- **Цена:** на ролике веранды стоящие у стола люди дольше остаются `unknown` — +1 спорный «визит» (EVAL.md §1.3).
  Для вебкамеры (`demo_webcam.yaml`) порог 5 с: сидящий близко к камере выглядит «стоящим».

## D-021. Калибровка под зал: только по команде, версии, откат
- **Что:** `calibrate collect → review → train → promote`; новая голова пишется в `models/site/<site>/vN/` и
  включается только `calibrate promote` (копия в `active.npz`), `calibrate rollback` возвращает прошлую.
  Авторазметка — только поведенческие правила (сидел ≥ 5 мин → гость; стоя у ≥ 3 столов → персонал), не
  предсказания модели; остальное — ручная проверка на локальной странице (лица размыты).
- **Почему:** модель не должна учиться на собственных ошибках без проверки человеком (WEEKEND_PLAN W6).

## D-022. При калибровке общие датасеты по умолчанию НЕ подмешиваются
- **Что:** `calibrate train` учит голову только на кропах зала; `--with-general` подмешивает 4 общих зала.
- **Почему:** кривая на отложенных залах (EVAL.md §8): «общие + 25 кропов зала» хуже, чем «только 25 кропов зала»
  (A: 0,63 против 0,80; B: 0,65 против 0,89; C: 0,75 против 0,95 balanced accuracy). Общие данные тянут голову
  к чужой форме.

## D-023. Состояние стола: классификатор и посуда выключены по умолчанию; «посуды не видно» ≠ «чисто»
- **Что:** `use_table_classifier` и `use_dish_detection` — `false`. Сигнал посуды голосует только «грязный»
  (`dish_absent_is_clean: false`). Правило согласия: «чистый»/«грязный» — когда так говорят ≥ 2 включённых
  сигнала (не больше числа включённых) и их больше, чем противоположных (`qonaq/logic/tablesignals.py`).
- **Почему:** на внешнем тесте классификатор стола — на уровне случайного (balanced accuracy 0,32 при 3 классах):
  в обучающих данных «грязный» = «другая камера». YOLOX нашёл посуду на 0–10% грязных столов и ни на одном чистом
  (EVAL.md §7): редкий, но надёжный голос «грязный». Эталон пустого стола остаётся основным сигналом.

## D-024. Синтетика: детерминированные кадры, отобранные фигуры, отдельные правила разметки
- **Что:** `python -m qonaq synth` рисует фигуры из датасетов (мягкая эллиптическая маска) на пустом кадре,
  разметку выводит из сценария по SPEC §5 (`qonaq/synth/scenario.py`), а не из кода логики. Фигуры отобраны
  из тех, что YOLOX уверенно видит (официант — sprite 9 зала C, гости — 13/31 из C/B): синтетика проверяет логику
  и пайплайн, а не детектор. Кадры без шума — одинаковые кадры попадают в кэш детекций (30-минутный сценарий
  считается минутами). Правило «сидели до старта» для синтетики выключено (ролик начинается с пустого зала).
- **«Ждут друга 30 минут»:** алерт «нет официанта» запрещён, а `long_service_without_visit` (900 с без визита,
  SPEC §5) ожидается — это другой алерт («гостей давно никто не проверял»), по SPEC он правильный.

# SPRINT2 (14.11.2026)

## D-025. Эмулятор регистратора: MediaMTX + ffmpeg без перекодирования, «субпоток» 960×540 12 кадр/с
- **Что:** `scripts/emulate_cameras.py` качает MediaMTX v1.21.2 (MIT) из релиза GitHub, сверяет SHA-256 с
  `checksums.sha256` релиза, один раз перекодирует ролики в H.264 960×540 12 кадр/с (GOP 2 с) и публикует их
  `ffmpeg -c copy -stream_loop -1` по путям Hikvision `/Streaming/Channels/<N>02` и Dahua `/cam/realmonitor`.
  Логин/пароль на чтение. Обрыв — `--outage-at/--outage-s` (сервер останавливается и поднимается).
- **Почему:** без перекодирования эмулятор почти не ест CPU (2 vCPU облака нужны пайплайну); субпоток — то,
  что мы и будем брать с регистратора (KZ_REALITIES). Версия закреплена — новые версии MediaMTX иногда меняют
  ключи конфига.
- **Ограничение:** MediaMTX не учитывает query в пути, поэтому Dahua-канал в эмуляции один и `channel=` любой
  «находится» — записано в PILOT_RUNBOOK.

## D-026. Потоки в многокамерном цикле читаются неблокирующе; подключение — в фоне
- **Что:** `VideoSource.poll()` для потоков отдаёт свежий кадр или `None` сразу; `Pipeline.step()` не ждёт
  молчащую камеру; подключение к потоку — в фоновом потоке источника (недоступная при старте камера не держит
  остальные). OpenCV открывает RTSP по TCP с таймаутами открытия/чтения 10 с; пауза переподключения 1→15 с.
- **Почему:** раньше `read()` пропавшей камеры блокировал цикл навсегда — одна отвалившаяся камера останавливала
  все. Потолок паузы 30 → 15 с: после перезагрузки регистратора (1–2 мин) камера возвращается быстрее.

## D-027. Кэш текстовых подписей — маска uint8 на 1024 строки (утечка памяти в live)
- **Что:** `render/text.py` кэширует маску текста uint8 (h×w) вместо float32 RGBA, `lru_cache(1024)` вместо 4096.
- **Почему:** 60-минутный прогон 4 камер показал рост памяти ~14 МБ/мин (338 → 567 МБ за 17 мин). tracemalloc на
  том же пайплайне указал на кэш патчей: подписи с таймерами («ждут 03:12») все разные, а патч float32 RGBA строки
  весит ~100 КБ → потолок кэша ~0,5 ГБ. Теперь потолок ~10 МБ. Цифры — EVAL §14.

## D-028. Три чата Telegram и правила очереди
- **Что:** `TELEGRAM_CHAT_ID` — администратор (алерты с кнопкой «Неверно»), `TELEGRAM_VENUE_CHAT_ID` — владелец
  заведения (итоги дня в `alerts.shift_summary_at`), `TELEGRAM_OWNER_CHAT_ID` — владелец системы (тех. сводка,
  проблемы с камерами, в т.ч. «камера снова работает»). Тексты — с местным временем и «Стол N» (`T05` → «Стол 5»),
  без названия заведения (включается `alerts.show_site_name`). Очередь: позже 2 мин — пометка «доставлено с
  опозданием», старше 30 мин — не отправлять (остаётся в журнале). Базовый URL — `TELEGRAM_API_BASE`.
- **Почему:** администратору нужно действие «подойти к столу 5», владельцу — итоги, нам — техника; смешивать их
  в одном чате — верный способ, чтобы бота замьютили. «Гости ждут 3 мин», доставленное через час, вредно.
- **Альтернатива:** один чат с хэштегами — отклонено по той же причине.

## D-029. `qonaq setup`: RTSP DESCRIBE вместо OpenCV для перебора; стоп после двух 401
- **Что:** шаблоны Hikvision/HiWatch, Dahua/Imou, Uniview, XMeye проверяются RTSP-запросом DESCRIBE (Basic/Digest)
  на канале 1; подошедший шаблон — по каналам 1..16 до трёх пропусков подряд. Два ответа 401 подряд — стоп
  с сообщением «неверный пароль». Пароль — только в `.env`; в URL кодируются только `@ : / ? # %`.
- **Почему:** DESCRIBE за доли секунды различает «нет канала» (404) и «неверный пароль» (401), OpenCV — нет.
  Регистраторы блокируют пользователя после 5–7 неудачных входов (Hikvision — на 30 мин): перебирать пароль
  или шаблоны дальше опасно для пилота. Частичное кодирование — не все прошивки/FFmpeg раскодируют %XX.

## D-030. Служба: systemd unit / задача Планировщика + cmd-обёртка с циклом
- **Что:** `qonaq service install`: Linux — unit `Restart=always`, `RestartSec=10`, `MemoryMax=3G`
  (без root — пользовательский unit + linger); Windows — задача «при запуске» от SYSTEM запускает
  `runs/qonaq-<объект>.cmd`, которая перезапускает live через 10 с (пауза через `ping`: `timeout` без консоли
  не работает). Лог — `runs/service_<объект>.log`, ротация 10 МБ × 5 (`QONAQ_LOG_FILE`).
- **Почему:** NSSM — лишняя скачиваемая программа; у schtasks нет флага «перезапускать при сбое» в командной
  строке (только через XML), а цикл в обёртке надёжен и прозрачен. Проверено только генерацией файлов и
  `systemd-analyze verify` (в облаке нет systemd как PID 1 и нет Windows).

## D-031. Синтетическая неделя — без видео, через настоящую логику
- **Что:** `python -m qonaq synth-week` генерирует план посадок (поток гостей по часам, логнормальные подход
  официанта, визит, уборка, «в пик медленнее», терпение гостей, очередь у входа) → наблюдения «кто в зоне стола»
  каждые 3 с → `RestaurantEngine` → журнал (epoch, UTC+5). «Как есть» и «после» отличаются только параметрами
  персонала (`configs/synth_week/`).
- **Почему:** неделю видео на 2 CPU не отрендерить и не продетектировать; а отчёт пилота считается из событий,
  так что для его проверки достаточно настоящей логики на правдоподобных наблюдениях. Видео-синтетика (W4)
  по-прежнему проверяет детектор+роли+логику на коротких сценариях.
- **Находки:** неделя нашла две ошибки: (1) уборка, начавшаяся до подтверждения ухода и закончившаяся после,
  терялась (стол «не убран» до следующих гостей, ложный алерт) — исправлено в `logic/restaurant.py`;
  (2) сессии в журнале затирались после перезапуска (ключ (камера, стол, sid), а sid после рестарта службы
  начинаются заново) — ключ теперь с `seated_ts`, старые журналы мигрируются при открытии.

## D-032. Отчёт пилота: деньги — только пик, уходы отдельно; бутстрэп-интервал для медианы
- **Что:** `report pilot`: главная цифра потерь — лишний простой неубранных столов в часы пик (как в отчёте смены,
  SPEC §7), «в месяц» = день × 30; уходы «не дождавшись» — отдельной строкой, в итог не входят. Для разницы
  медиан подхода — 95% бутстрэп-интервал с фразой «похоже / не похоже на случайность». Все показатели — «в день»
  (дни с посадками), чтобы периоды разной длины сравнивались.
- **Почему:** уход без заказа система видит хуже всего (EVAL §13) — это самая неуверенная цифра, её нельзя класть
  в итог для владельца. Интервал защищает от «улучшения», которое на самом деле шум недели.

## D-033. Детектор по умолчанию для тёмных угловых камер: плитки только вокруг зон столов; два профиля
- **Что:** новые настройки `detector.roi_tiles` (плитки только в прямоугольнике вокруг зон столов +15%) и
  `detector.detect_every` (детектор раз в N кадров камеры, между ними — последние рамки). Профиль «CPU мини-ПК,
  2–4 камеры» (`configs/sites/profile_cpu_minipc.yaml`): `yolox_m` INT8 + 2 плитки в ROI + 2 кадр/с + детектор через
  кадр. Профиль «GPU, 8 камер» (`profile_gpu.yaml`): `yolox_m` fp32 + 2 плитки в ROI, каждый кадр. Значения
  по умолчанию в коде (`yolox_s`, без плиток) **не меняются** — профиль включается при установке (`setup` пишет
  `yolox_s`; в PILOT_RUNBOOK — шаг «скопировать блок detector из профиля»), чтобы не ломать старые конфиги и тесты.
- **Почему:** EVAL §15: без плиток на угловой камере лёгкие модели видят 6–13% людей за столами; ROI при той же
  цене даёт +17–19 п.п.; `yolox_m` INT8 + ROI (0,71 за 587 мс) лучше `yolox_s` fp32 + ROI (0,56 за 610 мс).
- **Разметка S2 — 10 кадров вместо 30–40** и не независима от `yolox_l` (предразметка + ручная проверка): ручная
  разметка плотного тёмного зала через просмотр картинок без инструмента разметки — часы. Для честной цифры —
  разметить 30 кадров своей камеры в Label Studio (у владельца он есть) и прогнать `scripts/bench_detector.py`.
- **Отклонено:** NanoDet-Plus (Apache-2.0, ONNX есть) — хуже `yolox_s`; RT-DETR / D-FINE — нужен экспорт через
  PyTorch, в облаке не проверены; 4 плитки в ROI — дороже и хуже 2.

## D-034. Демо-ролик: титры по моменту, когда событие видно на панели; реальный кусок — с 36-й секунды; не для публикации
- **Что:** титры `demo-reel` ставятся в `detected_ts` события (посадка видна на панели через `seat_min_s`, уход —
  через `leave_min_s`), а в промежутках — пояснения «гости садятся — проверяем, что это не прохожие» и «гости вышли —
  1:30 ждём, не вернутся ли». Кусок реальной веранды берётся с 36-й секунды (`--real-from`).
- **Почему:** первая сборка (прошлая сессия) показывала «Гости сели» над столом со статусом «свободен», «Официант
  подошёл» — пока панель ещё «ждут», а на веранде — людей за «свободными» столами (в первые 30 с статусы ещё не
  установились: `preexisting_grace_s`). Владелец заведения увидит такое расхождение первым.
- **Ограничение (важно):** фон синтетики `topdown_cafe_empty` — превью стокового ролика с водяным знаком iStock,
  веранда — запись новостного канала (логотип в кадре). Оба — чужие ролики с GitHub (docs/DATA_SOURCES.md:
  «только для внутреннего тестирования»). Ролик можно показывать лично на встрече, но не публиковать и не
  рассылать. Для рекламы — пересобрать на своей записи (`--real`, свой фон в сценарии `configs/synth/demo_reel.yaml`).

## D-035. Обрыв камеры «замораживает» время в фильтрах присутствия
- **Что:** `PresenceFilter.on_gap(a, b)` сдвигает все отметки фильтра (окно наблюдений, `since`, последний
  положительный кадр) на длину обрыва; `TableMachine` вызывает его для обоих фильтров, когда между наблюдениями
  больше `blind_gap_s` (15 с). Время вслепую не считается ни присутствием, ни отсутствием.
- **Почему:** повторный прогон RTSP с обрывом (EVAL §14.1) показал: первый кадр после переподключения — без
  подтверждённых гостей (трекер и роли прогреваются), фильтр выключался задним числом от кадра до обрыва, и
  2 минуты вслепую давали «гости ушли» → «сели за неубранный стол» → ложный алерт через 40 с. На пилоте
  регистратор перезагружается или роутер моргает несколько раз в неделю — каждый раз это ломало бы сессии на
  всех занятых столах и портило метрики «время визита» и «уходы».
- **Альтернативы:** (1) после обрыва закрывать все сессии как «неизвестно» — честно, но теряет визиты целиком;
  (2) игнорировать N секунд после переподключения — магическое число, зависит от трекера. Отклонены.
- **Следствие:** если гости реально ушли во время обрыва, уход зафиксируется через `leave_min_s` после возвращения
  картинки (а не задним числом на момент обрыва) — время визита у такой сессии завышено на длину обрыва. Это
  лучше, чем ложный уход у всех.
