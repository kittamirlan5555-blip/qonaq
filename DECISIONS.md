# DECISIONS — решения, принятые без владельца

Формат: что решил → почему → какие были альтернативы. Новые решения — в конец.

## D-001. Python 3.12, окружение `.venv`, установка через `pip install -e .`
- **Что:** проект — обычный пакет с `pyproject.toml`; базовая установка `pip install -e ".[dev]"`,
  Ultralytics — опциональная группа `pip install -e ".[yolo]"`.
- **Почему:** одинаково работает на Windows и Linux, точка входа `python -m qonaq ...`.
- **Альтернативы:** poetry/uv-lock (лишняя сложность для MVP), requirements.txt (хуже с опциональными группами).

## D-002. Детектор только за интерфейсом `Detector`; Ultralytics — AGPL-3.0
- **Что:** весь код работает с `qonaq.detect.base.Detection` / `Detector`. `ultralytics` импортируется
  в единственном файле `qonaq/detect/ultra.py`. Ни один объект ultralytics не выходит за адаптер.
- **Почему:** Ultralytics YOLO распространяется под AGPL-3.0. Для коммерческого продукта придётся либо
  купить Enterprise-лицензию Ultralytics, либо заменить детектор. Интерфейс делает замену делом одного файла.
- **Альтернативы:** RT-DETR/D-FINE (Apache-2.0), YOLOX (Apache-2.0, см. D-003), собственная модель.

## D-003. Второй детектор «из коробки»: YOLOX через onnxruntime; `backend: auto`
- **Что:** добавлен адаптер `qonaq/detect/onnx_yolox.py` (YOLOX, Apache-2.0, готовые ONNX-веса из релиза
  на GitHub, инференс через `onnxruntime`). В конфиге `detector.backend: auto` означает:
  «ultralytics, если он установлен (стек по умолчанию из CLAUDE.md), иначе YOLOX-ONNX».
  `onnxruntime` — в базовых зависимостях, поэтому `pip install -e .` даёт рабочую систему без PyTorch.
- **Почему:** (1) в облачной сессии CPU-сборка PyTorch недоступна: `download.pytorch.org` закрыт сетевой
  политикой, а сборка с PyPI тянет ~3 ГБ CUDA-библиотек со скоростью < 1 МБ/с; (2) YOLOX под Apache-2.0 —
  это как раз кандидат на замену AGPL-детектора в коммерческой версии; (3) на рабочем ноутбуке утром
  установка без PyTorch занимает минуту.
- **Цена:** веса YOLOX старее (2021), на мелких людях слабее YOLO11. Компенсация — режим `onnx_tiles: 2`
  (полный кадр + две перекрывающиеся половины) и модель `yolox_m`. Сравнение — в `docs/EVAL.md`.
- **Альтернативы:** ждать установку torch (час+ и риск), экспортировать YOLO11 в ONNX (нужен torch и остаётся AGPL).

## D-004. `supervision` закреплён `<0.27`
- **Что:** в зависимостях `supervision>=0.22,<0.27`.
- **Почему:** в свежих версиях (проверено на 0.31.5) `sv.ByteTrack` удалён из пакета (трекеры вынесены
  в отдельный проект `trackers`). 0.26.x содержит ByteTrack и всё нужное.
- **Альтернативы:** пакет `trackers` (тянет лишние зависимости), свой трекер (незачем).

## D-005. В выходное видео попадают только обработанные кадры
- **Что:** аннотированное/демо-видео пишется с частотой `process_fps` (а не с частотой исходника).
- **Почему:** блюр привязан к детекциям конкретного кадра. Если дублировать рамки на пропущенные кадры,
  у идущего человека лицо «выезжает» из размытой области — это нарушение приватности. Заодно быстрее.
- **Альтернативы:** интерполяция рамок между кадрами (сложнее, всё равно риск утечки лица).

## D-006. Блюр: пикселизация верхней части bbox, включая неуверенные детекции
- **Что:** размывается верх bbox каждого человека (38% высоты для стоящих, 50% для «квадратных» bbox сидящих),
  причём для блюра берутся и детекции ниже порога трекинга (`detector.blur_conf`, по умолчанию 0.12).
  Блюр включён по умолчанию для любого сохраняемого кадра/видео; `privacy.save_raw_video` жёстко `false`.
- **Почему:** пропущенный детектором человек = неразмытое лицо; снижая порог только для блюра, уменьшаем
  этот риск без влияния на логику. **Ограничение:** человек, которого детектор не увидел совсем, останется
  неразмытым — перед публикацией ролик надо просмотреть глазами.
- **Альтернативы:** отдельный детектор лиц (ещё одна модель; на CCTV лица мелкие и находит он их хуже, чем людей).

## D-007. Видео пишется в H.264 через ffmpeg из пакета `imageio-ffmpeg`
- **Что:** кадры идут по pipe в ffmpeg (`libx264`, `yuv420p`, `+faststart`). Если ffmpeg не найден — OpenCV `mp4v`.
- **Почему:** `mp4v` из OpenCV не проигрывается в браузере и Telegram; демо-ролик должен открываться везде.
  `imageio-ffmpeg` ставит бинарник ffmpeg через pip и на Windows, и на Linux.

## D-008. Занятость стола — по скользящему окну присутствия, а не по id треков (SPEC §9a п.1)
- **Что:** `PresenceFilter`: окно `dropout_tolerance_s` (5 с), «включено» при доле положительных наблюдений
  ≥ 70%, «выключено» при ≤ 20%. Моменты событий выставляются задним числом (посадка = первое появление,
  уход = последнее наблюдение), поэтому гистерезис не искажает длительности.
- **Почему:** ByteTrack на косых камерах меняет id; таймеры стола не должны от этого сбрасываться.

## D-009. Как отличается визит персонала от «подсевшего гостя» без калибровки формы (SPEC §9a п.3)
- **Что:** у занятого стола каждый «не гость» открывает эпизод визита. Подтверждённый персонал (форма /
  ≥3 столов) засчитывается сразу при ≥ `visit_min_s`. Неизвестный засчитывается **после ухода**, если пробыл
  4–90 с, с `confidence: low`; если роли за это время признали его гостем — эпизод отменяется.
  Время реакции считается до **начала** визита.
- **Почему:** иначе опоздавший друг, подсевший к столу, считался бы «подходом официанта».
- **Следствие:** без калибровки формы статус SERVED появляется с задержкой на длительность визита;
  отчёт помечает долю событий с низкой уверенностью.

## D-010. Стол, занятый с первых секунд наблюдения, считается уже обслуженным
- **Что:** если гости сидят с самого старта потока (≤ `preexisting_grace_s`), сессия помечается
  `preexisting` и сразу переходит в SERVED; время подхода официанта для неё не считается.
- **Почему:** мы не знаем, сколько они уже сидят. Иначе каждый перезапуск системы давал бы ложные
  алерты «3 минуты без официанта» по всем столам. На коротких тестовых роликах это значит, что
  большинство столов сразу синие (SERVED) — это честно.

## D-011. Уборка, случившаяся до подтверждения ухода
- **Что:** уход гостей подтверждается через `leave_min_s` (90 с). Визиты персонала в этом окне
  откладываются: если гости вернулись — это обычные визиты; если уход подтвердился и был визит
  ≥ `clean_min_s` — стол сразу FREE, событие `cleaned` с реальным временем уборки.
- **Почему:** хороший официант убирает стол через 20 секунд после ухода; без этого правила такой стол
  висел бы «грязным» до следующего случайного визита.
